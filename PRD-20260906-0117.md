## Ringkasan Eksekutif

Platform sudah solid sebagai **katalog + pemesanan manual**: 8 vertikal produk,
multilingual penuh (EN/ID + ekstensibel), multi-currency, wallet/cashback,
referral, promo codes, admin kustomisasi homepage. Tiga celah terbesar:

1. **Tidak ada pembayaran nyata** — semua booking berakhir `pending` dan
   dikonfirmasi manual via WhatsApp.
2. **Tidak ada email sama sekali** — klaim "cek email Anda" di beberapa pesan
   saat ini misleading.
3. **Tidak ada SEO dasar** — meta description, sitemap, structured data nihil,
   padahal model bisnis bergantung trafik organik.

Dokumen ini menjabarkan semuanya ke dalam 10 inisiatif berprioritas, lengkap
dengan user stories, kriteria penerimaan, ketergantungan, dan estimasi bobot.

## P0 — Transaksi & Kepercayaan (wajib sebelum scaling)

### I-1. Payment Gateway (Midtrans Snap)

**Masalah**: Booking (tour/hotel/flight/train/transfer/attraction/esim) masuk DB
dengan status `pending`, lalu dikonfirmasi manual oleh admin lewat WhatsApp.
Tidak ada pembayaran online — potensi revenue bocor, admin overload, pengalaman
user tidak lengkap.

**Solusi**: Integrasi **Midtrans Snap** (pop-up payment, mendukung VA BCA/BNI/BRI/
Mandiri, GoPay, ShopeePay, QRIS, kartu kredit — pas untuk pasar Indonesia).
Arsitektur tetap vanilla PHP (tanpa composer bila memungkinkan; Midtrans PHP
SDK opsional — Snap via redirect/popup cukup dengan lib curl sendiri).

**User stories:**
- Sebagai pembeli, saya ingin membayar booking dengan VA/e-wallet/QRIS dan
  halaman otomatis berubah jadi "Lunas" tanpa tunggu admin.
- Sebagai admin, saya ingin notifikasi pembayaran masuk (webhook) dan daftar
  pembayaran di admin.
- Sebagai owner, saya ingin bukti transaksi yang sah (invoice + order ID
  Midtrans) untuk rekonsiliasi.

**Kriteria penerimaan:**
- Tombol "Bayar Sekarang" di booking-success & my-bookings → Snap popup.
- Webhook `payment-notification` (endpoint publik, verifikasi signature sha512)
  → update status `pending → paid/confirmed`, tulis `payment_records`.
- Idempotent: webhook berulang tidak membuat duplikasi status/earn wallet.
- Expiry & fallback: order kedaluwarsa → status `expired`; admin bisa re-invoice.
- Sandbox mode via setting (toggle produksi/sandbox di admin settings).
- Semua string baru bilingual; audit translations missing = 0.
- E2E: alur bayar sukses (emulasi webhook sandbox), bayar kedaluwarsa, webhook
  duplikat, akses webhook tanpa signature valid ditolak.

**Dependensi**: Tidak ada (bisa langsung mulai).
**Estimasi bobot**: Besar (± 2 fase: backend payment + admin/dashboard).
**Risiko**: Verifikasi signature & replay attack → wajib signature check + log;
lingkungan sandbox vs produksi → setting terpisah.

### I-2. Infrastruktur Email Transaksional

**Masalah**: Tidak ada pengiriman email di seluruh codebase. Newsletter menyimpan
subscriber tapi tidak pernah mengirim apa pun. Konfirmasi booking, invoice,
reset password, semuanya tergantung WhatsApp manual.

**Solusi**: Abstraksi `sendEmail($to, $subject, $htmlBody, $opts)` di
`includes/email.php` — driver SMTP via PHPMailer **atau** lib curl ke API
(resend/mailgun — lebih sederhana tanpa composer). Template HTML sederhana
(brand, dark header, tombol CTA) di `includes/email-templates/`.

**Email wajib (v1):**
1. Konfirmasi booking (dengan kode, detail, tombol Bayar/Track)
2. Status berubah (confirmed / cancelled)
3. Invoice PDF-free (HTML invoice dengan rincian harga)
4. Reset password (bergantung I-3)
5. Welcome/verify saat register (opsional v1.1)

**Kriteria penerimaan:**
- `sendEmail()` queue-safe: gagal kirim tidak menggagalkan booking (log ke
  tabel `email_log`: penerima, subject, status, error, retry count).
- Kirim terpicu oleh event: booking dibuat, webhook payment, admin ubah status.
- Template bilingual mengikuti bahasa user (kolom `lang` di users — tambah
  bila belum ada) — fallback ID.
- Admin page kecil "Email Log" (filter gagal → resend manual).
- Setting SMTP/API di admin (pola wa-settings).
- E2E: event booking memicu baris email_log; resend manual; template EN/ID.

**Dependensi**: I-1 untuk konten invoice/payment (bisa paralel untuk email #4).
**Estimasi bobot**: Sedang.
**Risiko**: Deliverability (SPF/DKIM) → dokumentasikan setup DNS; jangan kirim
dari domain utama tanpa konfigurasi.

### I-3. Reset Password & Verifikasi Akun

**Masalah**: Tidak ada "Lupa Password". Register langsung aktif tanpa verifikasi
email (rentan akun fake).

**Solusi**: Tabel `password_resets` (token, expiry, used). Flow standar:
lupa password → email token → halaman set password baru. Opsional v1.1:
verifikasi email saat register (status `unverified` dulu).

**Kriteria penerimaan:**
- Link "Lupa password?" di login → form email → email berisi link 1 jam.
- Token sekali pakai, kedaluwarsa, dan invalid → pesan jelas.
- Password baru ≥ 6 karakter (konsisten register).
- Rate limit permintaan token (1x/menit per email).
- Bilingual penuh; E2E: minta token, set password baru, login, token lama tidak
  berlaku.

**Dependensi**: I-2 (email).
**Estimasi bobot**: Kecil–Sedang.

## P1 — Pertumbuhan Organik

### I-4. SEO Dasar

**Masalah**: Tidak ada meta description, sitemap.xml, robots.txt, structured
data. Untuk bisnis OTA, trafik organik = sumber booking termurah.

**Solusi (v1, tanpa CMS):**
- `sitemap.php` dinamis: index + tours/hotels/attractions/transfers/trains/esim
  (slug aktif) + halaman statis; `robots.txt` mengarah ke sitemap.
- Meta description per halaman (dari deskripsi DB, terpotong 160 char) +
  Open Graph (og:title/og:image/og:description) untuk share WhatsApp/social.
- JSON-LD: `Product`/`TouristTrip` (tour-detail), `Hotel` (hotel-detail),
  `Organization` + `WebSite` (index), `BreadcrumbList`.
- Canonical URL per halaman.
- Admin: field `meta_title`/`meta_description` opsional per tour/hotel
  (fallback otomatis bila kosong) — bergaya field EN yang sudah ada.

**Kriteria penerimaan:**
- sitemap.xml valid (XML, <50k URL), robots.txt benar.
- Semua detail page punya meta description unik & OG tags (cek via E2E meta).
- JSON-LD valid (bisa diuji rich results).
- i18n: `hreflang` id/en di halaman publik (opsional v1.1).
- E2E: meta & JSON-LD muncul di 3 halaman kunci; sitemap berisi ≥ 1 URL per
  tipe konten.

**Dependensi**: Tidak ada. **Estimasi bobot**: Kecil–Sedang.

---

### I-5. Modul Blog / Artikel

**Masalah**: Footer menjanjikan "blog TourAndTravel" — tidak ada module-nya.
Blog = mesin SEO (artikel destinasi → internal link ke paket).

**Solusi**: Tabel `posts` (title, slug, excerpt, body, cover_image, category,
tags, status, published_at, content_language, title_en/body_en …). Admin CRUD
(sama ergonomi dengan tour). Halaman publik: daftar + detail + widget "artikel
terkait" di tour-detail. Sitemap otomatis (gabung I-4).

**Kriteria penerimaan:**
- Admin CRUD lengkap (draft/publish, upload cover, slug otomatis).
- Publik: list (pagination), detail dengan heading terstruktur, related tours.
- Bilingual (kolom _en + fallback, pola tContent).
- Tampil di sitemap & punya meta/OG (dari I-4).
- E2E: CRUD + render publik + tidak muncul draft.

**Dependensi**: I-4 (untuk sitemap/meta — bisa dibangun dulu tanpa blog).
**Estimasi bobot**: Sedang.

---

### I-6. Notifikasi Status Booking ke User

**Masalah**: WA hanya dikirim ke admin. User tidak tahu booking-nya dikonfirmasi
tanpa mengecek halaman track.

**Solusi (v1): in-app notification + email** (bergantung I-2). Tabel
`notifications` (user_id, type, payload JSON, read_at). Ikon lonceng di navbar.
Trigger: booking dibuat, dibayar, dikonfirmasi, dibatalkan. v1.2: WA user via
WUZAPI (infra sudah ada — tinggal kirim ke nomor user, perlu consent).

**Kriteria penerimaan:**
- Lonceng + badge unread; halaman notifikasi; mark-as-read.
- Email ringkasan per event (I-2).
- E2E: aksi booking → notifikasi muncul untuk user terkait saja.

**Dependensi**: I-2 (email), I-1 (event paid). **Estimasi bobot**: Sedang.

## P2 — Penguatan Produk Existing

### I-7. Admin Analytics Dashboard

- Grafik booking/minggu (30 hari), revenue per vertikal, top tours/hotels,
  status funnel (pending/paid/cancelled), subscriber & wishlist growth.
- Bukan library berat: chart via inline SVG atau CDN Chart.js satu file.
- Sumber: tabel existing (bookings, wallet_transactions, payments).
- Kriteria: dashboard memuat < 2s, angka cocok dengan DB (query yang sama
  dipakai E2E), filter rentang tanggal.
- **Estimasi bobot**: Sedang. **Dependensi**: lebih berguna setelah I-1.

### I-8. Review Kaya (foto, balasan, utilitas)

- Upload foto ulasan (max 3, konvensi upload existing), balasan admin per
  review, sort (terbaru/tertinggi), filter bintang, ringkasan distribusi bintang
  di tour-detail.
- Kriteria: foto tampil di galeri review, balasan admin berbeda visual, semua
  input di-sanitasi (pola abuse-xss existing), bilingual.
- **Estimasi bobot**: Kecil–Sedang.

### I-9. Kupon & Referral Upgrade

- Halaman "Kupon Saya" (promo aktif untuk user, yang sudah dipakai, expiry).
- Reminder email notifikasi expiring promo (I-2).
- Referral: halaman leaderboard + status reward lebih jelas (existing hanya
  total).
- **Estimasi bobot**: Kecil.

## Urutan Eksekusi yang Disarankan

```
Sprint A (transaksi):    I-1 Payment  ──→  I-2 Email  ──→  I-3 Reset Password
Sprint B (organik):      I-4 SEO       ──→  I-5 Blog
Sprint C (retensi):      I-6 Notifikasi ──→ I-7 Analytics
Sprint D (polish):       I-8 Review kaya, I-9 Kupon, I-10 UI/UX (paralel kecil-kecil)
```

**Kenapa urutan ini**: Payment & email menyelesaikan lingkaran transaksi
(revenue). SEO + blog membangun pipa trafik yang butuh waktu matang (mulai
cepat = untung). Notifikasi & analytics bernilai maksimal setelah transaksi
berjalan. Polish tidak mengunci apa pun dan bisa diselipkan.

## Definisi Selesai Global (berlaku semua inisiatif)

- [ ] Semua string baru bilingual (`t()` / `tContent()` / `I18N.t()`); audit
      translations **missing = 0**
- [ ] E2E baru per fitur; full suite `--workers=1` tanpa failure baru
- [ ] `php -l` semua file; konvensi repo (kebab-case, admin guard, flash msg)
- [ ] Migration DB idempotent; schema.sql/schema-klook.sql ikut diperbarui
- [ ] Smoke manual id/en tercatat di `.omo/plans/`
- [ ] Commit per fase + push; `git status` bersih

## Kriteria "Tidak Dikerjakan" (penjaga scope)

- Tidak mengganti framework/stack (tetap PHP vanilla + Bootstrap 5)
- Tidak menambah vertikal produk baru sebelum payment beres
- Tidak membangun CMS blog penuh (cukup posts sederhana)
- Tidak melakukan redesign visual global (ikuti design tokens existing)
